# 实例生命周期

[返回入口](README.md) · [HMCL 对照](hmcl-reference.md) · [状态与恢复](state-and-recovery.md)

本文件定义 LumilioCL 的目标业务语义；明确写成「当前」的部分来自实际 core 与 behavior。路径、恢复和迁移仍以 App State 及 ADR 的状态为准。流程归属现有 Library / Discover / Activity / Instance，不新增导航。

## 对象与共同规则

- 实例是稳定 ID、显示名称、游戏/加载器配置与独立可变游戏目录的组合。改名不改变 ID、profile 路径、历史关联和集合关系。
- 游戏版本与加载器组合决定共享 release 身份；多个实例可以引用同一 meta，不能共享可写的 mods、世界或游戏配置。
- 收藏、集合是库记录；磁盘文件不是收藏、名称、集合关系的替代来源。目录缺失必须保留库记录并展示问题。
- 安装状态、完整性、活动、会话与诊断是不同事实；一个 `installed` 标志不能证明当前可启动，也不能证明游戏运行中。
- 配置向导在提交前只保存草稿。执行操作绑定目标 ID、版本、来源及输入，不跟随之后的“当前实例”选择变化。
- 当前 core 的 `create_instance` 创建记录，首次 launch 可以补安装；业务设计必须区分“实例已创建”和“安装已完成”。

## L-LIB-01 — 查找、选择与组织实例

参考：H-NAV-01/03/04、H-INSTANCE-01。入口：Home 的 Continue/Recent、Library 的 All Instances/Favorites/User Collections。

主线：读取库快照 → 展示加载/空库/结果 → 搜索或筛选 → 选择实例 → 进入 Overview 或发起启动。收藏和集合操作写 launcher.db；选择、搜索、滚动和当前路由保存在 UI 内存，重启默认不恢复导航。

分支：缺目录或不完整的实例仍可查看 Diagnostics；没有可继续项时不伪造 Continue。Home 是库、会话及诊断的投影，不再维护一份实例事实。删除集合只删除组织关系，不删除实例和游戏文件；同一实例可属于多个集合。

成功：持久组织变更立即反映到相关列表，重启仍在；失败保持原持久事实并提示。切换实例只影响随后发起的操作，当前活动仍指向原实例。

当前：store 支持收藏、集合、稳定 ID 和改名；Home 的 attention 规则已经存在。真实 Library 的收藏和实例管理入口已接入；其他组织 UI 入口仍需另验，不从 core 能力推断。验收：AC-LIB-01、AC-LIB-02、AC-RACE-01。

## L-LIB-02 — 创建并安装游戏实例

参考：H-NAV-02、H-INSTALL-01/02。入口：Library 创建流程；空库快捷流程属于 Home，但仍复用同一业务服务。

1. 选择游戏版本；省略时按明确的默认策略获取版本，不在请求失败时猜一个版本。
2. 选择原版或加载器及版本，输入显示名称；验证当前实现是否可安装且可启动。
3. 展示配置摘要并提交。明确用户选择的是“只创建”还是“创建并安装”；后者注册 Activity。
4. 下载/复用共享资源 → 校验 → 发布安装事实 → 刷新库及 Overview。原版和加载器资源不进入实例可变目录。
5. 只有用户选择安装后启动的快捷流程，才在安装成功后衔接 L-PLAY-01；普通安装不暗中启动游戏。

失败：元数据/加载器列表获取失败时不创建错误配置。记录已经创建但安装未完成时显示未安装/失败，不冒充 ready；取消后的临时文件与已校验共享文件按状态与恢复规则处理。最新版本与兼容策略属于 core，不由 UI 拼接。

当前：创建和首次启动的服务行为见 [service](../behavior/service.md)。Forge/NeoForge 的 launchable 限制必须按实际实现保留；参考里的选项不等于当前支持列表。验收：AC-INSTALL-01、AC-INSTALL-02、AC-OFFLINE-01。

## L-LIB-03 — 获取和导入整合包

参考：H-INSTALL-03..07、H-DISC-04。入口：Discover.Modpacks 或 Library 导入；线上获取归档和本地导入最终进入同一格式解析/安装契约。

主线：选定归档及来源 → 识别格式 → 读取游戏/加载器、文件与覆盖项 → 确认新实例配置 → 绑定稳定 ID → 创建隔离实例 → 安装及校验 → 发布结果。整合包创建实例，普通模组/资源包/光影安装到已有实例。

首轮格式是当前 [modpack](../behavior/modpack.md) 的 Modrinth mrpack；HMCL 支持的其他格式、URL 输入和 server manifest 仍是范围待决策项。解析必须拒绝危险路径与不支持的组合；限制来源、校验大小/hash；不把任意 ZIP 当整合包。

文件规则：仅在目标实例 game 中应用覆盖项；不覆盖其他实例和共享可变数据。客户端适用性、可选文件及覆盖优先级沿用现有 behavior；若用户要增加可选项选择，先更新契约与计划。

取消/失败：当前导入在暂存目录完成后才创建记录并发布（计划 0021），失败/取消不留半成品，崩溃由启动恢复补完或丢弃；本地 `.mrpack` 与在线下载共用同一导入。目标日志必须区分临时副作用、已校验共享资源和用户原有内容，不盲目删除一个后来已有用户文件的目录。

成功：库中出现新实例，Activity 记录结果；能否立即启动要按安装完整性和 Java/账户检查确定。验收：AC-PACK-01、AC-PACK-02、AC-OPS-02。

## L-LIB-04 — 重命名

参考：H-INSTANCE-02，刻意采用与 HMCL 不同的稳定身份规则。入口：Library/Instance 的实例操作。

主线：显示当前名称 → 输入并验证新显示名 → 一次提交库记录 → 更新全部投影。ID、profile 目录、共享 release、集合成员、正在运行会话和历史不改变。同一请求重复执行应保持同一结果。

取消不写入；持久化失败不得把只修改的内存状态显示为已保存。实例在操作前已删除则报告不存在，不自动重建。名称冲突策略由 store 现有校验决定，不能拿 HMCL 的目录名规则要求用户。

当前：service.rename 委托 store；store 在 SQLite 提交成功后才发布内存投影。只读、事务中途和提交失败测试覆盖旧值保留与重试；真实 Instance.Overview 可保存名称；失败保留输入并提供技术详情，保存后刷新 Library/Home。验收：AC-LIB-01、AC-PERSIST-01。

## L-LIB-05 — 复制实例

参考：H-INSTANCE-03；目标流程，当前没有完整实例复制服务。入口：Library/Instance 实例操作。

主线：选择源实例 → 新显示名 → 明确是否包含世界及其他可变文件 → 展示复制范围 → 创建新 ID → 准备独立文件副本 → 校验 → 发布新库记录。可复用不可变共享依赖；不能把可写游戏内容硬链接回源实例。

当前（计划 0021）：`copy_instance` 先在暂存目录完成独立副本再发布，可选是否带世界，不复制历史/快照/游玩时间，详见 [staged-instances](../behavior/staged-instances.md)。

目标不得覆盖已有实例。源游戏运行或有写操作时，按 L-OPS-01 的冲突规则阻止，或使用已证明一致的快照；不能把实时复制当一致副本。失败清理本次临时目标，不触及源实例或已有目标；复制完成前不显示 ready。

是否复制历史、快照及敏感服务器配置须在实施计划冻结范围，默认不宣称源身份/会话一并复制。验收：AC-COPY-01、AC-RACE-02。

## L-LIB-06 — 删除实例

参考：H-INSTANCE-04；归属 Library，后台结果由 Activity.Repairs/Diagnostics 承接。

主线：选定稳定 ID → 展示实例、世界和快照删除范围 → 检查运行/安装/恢复冲突 → 用户确认 → 写 pending-delete → 将 profile 移入同卷隔离区 → 完成数据库删除和磁盘清理。这是 App State 的目标；不是当前实现。

删除不能碰共享 meta、已安装 Java 或其他实例。删完当前查看对象时返回 Library，历史详情可以说明对象已删除；不能沿用悬空路由继续写入同 ID。UI 退出不代表后台删除完成。

失败：隔离或清理失败保留明确可定位的恢复信息，并提供重试或恢复路径。跨卷删除策略另定，不能用跨卷 rename 假装原子操作。重启对照日志、数据库和目录判定阶段，不直接重放删除。

当前实现（计划 0016）：service.delete_instance 先写 state/operations 日志，把 profile 同卷移入隔离区，再提交库删除，最后清理；各点失败会回滚或在下次启动完成，见 [deletion](../behavior/deletion.md)。删除确认与游戏库/游戏页的删除入口已接入；跨卷策略尚未实现。验收：AC-DELETE-01、AC-DELETE-02、AC-OPS-02。

## L-LIB-07 — 更新实例或加载器组合

参考：H-INSTANCE-06..08。与 L-CONT-03 的单个内容更新区分。已服务化（计划 0030）：更换游戏版本/加载器（`change_runtime`）与修复游戏文件（`repair_instance`）；整合包更新（识别包管理文件）仍未做。

主线：选定实例 → 获取更新来源和候选组合 → 检查协议及兼容性 → 展示将替换的配置/文件及用户文件影响 → 准备资源与必要备份 → 停止冲突写入 → 提交组合和文件 → 重新校验 → 写 Changes/Activity。

加载器变化建立新的共享 release 引用，不就地改写其他实例使用的组合。整合包更新需要识别由包管理的文件和用户自行增加/修改的文件；不把完整覆盖 game 当更新策略。

失败/取消：提交前保留旧可用版本；已经部分提交则记录实际边界并进入恢复，不能统一声称全部回滚。更新完成后仍做启动资格检查，不把下载成功当兼容通过。

当前 loader 安装及 content 更新是已有独立领域能力，不证明完整组合切换、包更新、离线组件安装已可用。验收：AC-UPDATE-01、AC-RACE-02、AC-OPS-02。

## L-LIB-08 — 导出整合包与备份

参考：H-INSTANCE-09、H-WORLD-09/10；整合包导出入口/格式待决策，App State 定义个人/完整离线备份目标。

| 目标 | 输入与范围 | 完成后可承诺 |
|---|---|---|
| 整合包分发 | 选择格式、包元数据和游戏内容，按协议生成文件清单/覆盖项 | 可由支持该格式的导入器安装；不是原机器完整恢复 |
| 世界归档 | 单个一致世界及名称/元数据 | 可导入为世界；不包含启动器账户和库 |
| 个人数据备份 | SQLite 一致快照、config、profiles，可选活动历史 | 保留个人数据；离线运行依赖可能要重新获取 |
| 完整离线备份 | 个人数据加 meta 和 runtimes | 在兼容平台/完整校验条件下保留离线依赖；不承诺跨架构直接运行 |

共同流程：确认目标 → 选择范围和位置 → 排除凭据、锁、cache 和临时文件 → 获取一致读取边界 → 写临时归档 → 校验 → 发布 → 报告实际包含项及限制。

运行中的世界不能承诺一致备份；先停止或使用已存在的一致快照。SQLite 不能在写入时只复制主文件。失败/取消不得用残缺归档覆盖已有成功备份；共享资源引用及平台条件在恢复时重新核对。当前 snapshots 的 Full 范围不包含 mods 等完整 game 内容，不能宣传为完整实例/离线备份。

验收：AC-BACKUP-01、AC-SNAPSHOT-01、AC-PERSIST-01。
