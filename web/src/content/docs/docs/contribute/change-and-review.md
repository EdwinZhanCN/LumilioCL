## 明确工作

1. 检查 Git 状态。
2. 找到相关代码和用户路径。
3. 定义可检查的验收条件。
4. 多步骤或跨会话工作应创建或更新 JSON 计划。
5. 实施前，把计划状态设为 `in_progress`。

计划示例是 `.agents/schemas/examples/proposed.json`。
计划契约见 `.agents/plans/README.md`。
使用稳定的计划和任务 ID。
backlog 条目变为计划后，从 backlog 移除。

## 实现修改

每个模块只负责一项职责。
非测试代码接近 800 行时，应拆分模块。
单元测试放在相邻的 `tests.rs` 或 `tests/` 模块。
公开 API 留在模块边界。

启动器文案写入语言目录。
同时补全中文和英文条目。
消息 ID 和参数遵循 `lumilio-i18n` skill。

每条已实现的用户路径都需要 `ia` 注释。

```rust
// ia[page]: 操作 | 层 / 组件 | 结果与反馈 [| 备注]
```

修改注释后，运行 `just ia`。
不要手改 `docs/ia/paths/`。
不要把计划中的功能声明为已实现路径。

UI 修改前，阅读 GPUI skills 和 `docs/design-language.md`。
检查亮色、暗色和减少动效状态。
只记录实际检查过的状态。

## 检查结果

1. 实施过程中，运行最窄的适用检查。
2. 交接前，修复每项失败。
3. 运行[开发环境](/docs/contribute/setup/#选择检查)列出的交接检查。
4. 完成必要的手动检查。

在正确边界测试行为。
领域测试不依赖 GPUI。
回归测试需暂时重新引入缺陷。
确认测试因该缺陷失败。
然后移除缺陷。
再次运行测试。

不要修改检查来隐藏失败。
不要声称未来 CI 会修复本地失败。

## 保持计划准确

1. 记录验证结果。
2. 记录决策、理由和后果。
3. 记录失败教训及防止再次发生的 guard。
4. 验收完成后，记录 outcome。
5. 把任务和计划标为 completed。
6. 运行 `just plans`。
7. 运行 `just plans-check`。

完成或取消后，保留 JSON 文件。
实际条件阻止进展时，使用 `blocked`。
记录阻塞条件和剩余任务。
完成不等于发布。

## 准备交接

说明问题和最终行为。
有助于评审时，提供修改前后的具体例子。
列出已通过的检查。
说明剩余手动检查或已知限制。
复杂修改提供更多细节。

Pull request 应说明最终实现。
不要要求评审者重建对话过程。

任务授权提交时：

1. 把已验证的修改提交到工作分支。
2. 推送到 fork 或已授权的仓库。
3. 向 `main` 创建 pull request。
4. 在描述中加入交接报告。
5. 合并前，解决检查失败。

改编代码应保留来源归属。
项目许可证是 `AGPL-3.0-only`。
分发修改后的应用前，阅读[许可证](https://github.com/EdwinZhanCN/LumilioCL/blob/main/LICENSE)。
